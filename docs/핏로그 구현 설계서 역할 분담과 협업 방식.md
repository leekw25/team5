# 핏로그 구현 설계서: 역할 분담과 협업 방식

Oct 6, 2026 · @이규원

## 개요

> **변경(2026-10-06):** 개발 방식이 "개발자별 별도 앱 → 멘토 통합"으로 바뀌었습니다. 개발 중에는 GitHub·Supabase를 쓰지 않고 로컬 JSON에 저장합니다. 진행 방식은 `전체 구성.html`, 기능 범위는 `요구사항 정의서 - A/B`를 기준으로 하며, 이 문서의 브랜치·PR 규칙은 통합 이후에 적용합니다.


이 설계서는 구현 초심자 2명과 멘토 1명이 3주 안에 시연 가능한 앱을 만드는 기준입니다. 개발자 2명은 기능별로 나눠 동시에 만들고, 멘토는 공유 규칙과 main 브랜치를 지킵니다. 두 기능은 '기록(Record)' 데이터 하나로만 만나므로, 이 약속을 먼저 정하면 서로 기다리지 않고 동시에 개발할 수 있습니다.

| 역할 | 담당 | 핵심 산출물 |
| --- | --- | --- |
| 개발자 A | 쉬운 입력 | 음성·텍스트·사진을 구조화된 기록으로 바꿔 저장하고 타임라인에 표시 |
| 개발자 B | 미션 성공과 달력 리워드 | 기록으로 미션 성공을 판정하고 축하 연출, 달력 스탬프, 연속 달성(스트릭) 표시 |
| 멘토 | merge와 코드 리뷰 | PR 리뷰와 merge, 공유 계약·DB 변경 관리, 통합 검증, 데모 빌드 |

범위는 기획안의 3분 시연이 실제로 동작하는 수준까지이고, 일정은 3주(15 작업일) 기준입니다. 날짜별 할 일은 3주 실행 체크리스트에, 운동 기록 방식과 건강 앱 연동 검토는 운동 기록·헬스 데이터 검토에 있습니다. AI 리포트(Insight) 화면은 시연에 나오지 않아 범위에서 뺍니다.

## 용어 풀이

처음 보는 용어는 이 표를 먼저 봅니다. 나머지 내용은 이 용어들을 알고 있다고 보고 썼습니다.

| 용어 | 쉬운 설명 | 이 프로젝트에서 |
| --- | --- | --- |
| 저장소(Repository) | 코드를 모아 두는 온라인 폴더 | GitHub에 하나 만들어 세 명이 함께 씀 |
| 브랜치(Branch) | 원본(main)을 건드리지 않고 작업하는 복사본 | 체크리스트 항목 하나마다 하나씩 |
| PR(Pull Request) | "내 작업을 원본에 합쳐 주세요"라는 요청 | 멘토가 보고 승인하면 합쳐짐 |
| merge | 작업 브랜치를 원본에 합치는 일 | 멘토만 함 |
| 충돌(Conflict) | 두 사람이 같은 곳을 고쳐 자동으로 합칠 수 없는 상태 | 직접 고치지 말고 멘토에게 요청 |
| Expo Go | QR 코드만 찍으면 개발 중인 앱을 휴대폰에서 보는 앱 | 개발과 시연 모두 이것으로 |
| Supabase | 로그인과 DB를 한 곳에서 주는 서비스 | 기록·미션 결과 저장 |
| Gemini API 키 | Google AI를 쓰기 위한 비밀번호 같은 값 | 코드에 넣지 않고 앱 설정 화면에서 입력, 휴대폰에만 저장 |
| 계약(Contract) | A와 B가 주고받는 데이터 모양에 대한 약속 | contract.ts 파일 하나 |
| 이벤트(Event) | "기록이 바뀌었다"는 앱 안의 알림 방송 | A가 보내고 B가 들음 |
| RLS | DB에서 "자기 데이터만 보기"를 강제하는 규칙 | 멘토가 설정 |
| 순수 함수 | 같은 입력이면 항상 같은 결과를 내는 함수 | 미션 판정, 스트릭 계산 |
| CI | PR을 올리면 자동으로 도는 검사 | 문법 검사, 타입 검사, 테스트 |
| 시드 데이터 | 시연을 위해 미리 넣어 두는 데이터 | 아침 기록, 미리 달성한 미션 2개 |

## 역할과 책임

P0만 끝나도 시연이 가능하도록 나눴습니다. P0은 시연에 꼭 필요한 기능, P1은 3주차에 여유가 있을 때 할 기능, P2는 시간이 남거나 발표 이후에 할 기능입니다. 초심자 3주 일정에 맞춰 미션은 도달형만 P0으로 두었습니다.

| 담당 | 작업 | 우선순위 | 완료 기준 |
| --- | --- | --- | --- |
| A | 텍스트 입력을 파싱해 기록으로 저장 | P0 시연 필수 | 시연 문장을 넣으면 싸이버거·감자튀김·제로콜라 3개 항목이 저장됨 |
| A | 음성 녹음과 음성 인식 | P0 시연 필수 | 마이크 버튼 한 번으로 저장까지 끝남 |
| A | 오늘의 기록 타임라인 | P0 시연 필수 | 저장 직후 타임라인에 항목이 추가됨 |
| A | 기록 변경 이벤트 발행 | P0 시연 필수 | 저장 성공 시 records:changed가 1회 발행됨 |
| A | 파싱 실패·불확실 처리 | P0 시연 필수 | 실패 시 다시 말하기와 직접 입력 안내가 나옴 |
| A | 빠른 기록 버튼(최근 운동 칩) | P0 시연 필수 | 칩을 한 번 탭하면 AI 없이 바로 저장됨 |
| A | 시연 문장 응답 캐시 | P0 시연 필수 | 네트워크가 끊겨도 시연 문장이 처리됨 |
| A | 사진으로 식단 입력 | P1 있으면 좋음 | 음식 사진 1장으로 메뉴와 탄·단·지 추정치가 저장됨 |
| A | iPhone 걸음 수 자동 반영 | P1 있으면 좋음 | 앱을 열면 오늘 걸음 수가 기록 1개로 갱신됨 |
| A | 기록 수정·삭제 | P2 여유 시 | 수정·삭제 후에도 이벤트가 발행됨 |
| B | 미션 카탈로그(도달형 4종)와 판정 함수 | P0 시연 필수 | 단백질·물·스쿼트·걸음 수 판정 테스트가 통과함 |
| B | 오늘의 미션 3개 배정(고정 세트) | P0 시연 필수 | 식단·생활·운동 각 1개가 매일 배정됨 |
| B | 이벤트 구독 후 판정과 상태 저장 | P0 시연 필수 | 기록 저장 후 1초 안에 미션 카드 상태가 바뀜 |
| B | 미션 성공 연출(폭죽 애니메이션) | P0 시연 필수 | 성공으로 바뀌는 순간 한 번만 재생됨 |
| B | 리워드 달력(달성 수 링, 완수 스탬프) | P0 시연 필수 | 날짜별 0\~3개 달성이 구분되고 3개면 스탬프가 찍힘 |
| B | 연속 달성(스트릭) 계산과 표시 | P0 시연 필수 | 테스트(오늘 미완료, 하루 끊김)가 통과함 |
| B | AI 1줄 코칭 | P1 있으면 좋음 | 하루 기록과 미션 결과로 1문장이 생성됨 |
| B | 배지 | P1 있으면 좋음 | 7일 연속 등 조건 달성 시 지급됨 |
| B | 회피형·구간형 미션(튀김, 가당 음료, 12시간 공복) | P2 여유 시 | 하루 마감 시점 판정 테스트가 통과함 |
| B | AI 미션 추천 | P2 여유 시 | 카탈로그 안의 미션만 추천됨 |
| 멘토 | 저장소, 브랜치 보호, CI 설정 | P0 시연 필수 | main에 직접 push가 막히고 PR마다 검사가 돎 |
| 멘토 | 공유 계약·이벤트·날짜 유틸, DB 마이그레이션 | P0 시연 필수 | A·B가 목업 데이터로 각자 개발을 시작할 수 있음 |
| 멘토 | 팀원 개발 환경 설치 지원 | P0 시연 필수 | 2일차 안에 A·B 모두 Expo Go로 첫 화면을 띄움 |
| 멘토 | 오늘 화면 조립(A·B 컴포넌트 배치) | P0 시연 필수 | 한 화면에서 입력부터 미션 성공까지 이어짐 |
| 멘토 | 코드 리뷰, merge, 통합 검증 | P0 시연 필수 | merge 후 main에서 시연 시나리오가 통과함 |
| 멘토 | 시연 시드 데이터와 리허설 | P0 시연 필수 | 시연 휴대폰에서 3분 시나리오를 2회 연속 성공 |

공유 영역(계약 타입, DB 변경, 오늘 화면 조립)은 merge 담당인 멘토가 맡는 것을 권장합니다. 두 개발자가 같은 파일을 고치는 일을 막아 merge 충돌이 크게 줄어듭니다.

## 아키텍처와 모듈 경계

A와 B는 서로의 코드를 직접 부르지 않습니다. A가 기록을 저장하면 '기록이 바뀌었다'는 이벤트만 보내고, B는 그 신호를 듣고 DB의 기록을 다시 읽습니다. 공유 영역과 DB 구조는 멘토가 관리합니다.

&#91;embedded content: 모듈 경계와 데이터 흐름 · 담당별 색 구분\]

앱 안에서는 이벤트로, 앱 밖에서는 records 테이블로 데이터가 넘어갑니다. AI 호출은 모두 `src/shared/gemini.ts`를 거칩니다.

스택은 Expo(React Native, TypeScript), Supabase, Gemini API입니다. Expo Go로 QR만 찍으면 휴대폰에서 바로 확인할 수 있고, Supabase는 로그인과 DB를 웹 대시보드에서 관리할 수 있습니다.

AI는 서버 함수 없이 앱에서 Gemini를 직접 부릅니다. API 키는 코드에 넣지 않고 사용자가 앱 설정 화면에서 입력하며, 휴대폰 보안 저장소(SecureStore)에만 저장됩니다. 서버 함수 배포·권한 관리가 사라져 초심자 부담이 줄고, 공개 저장소에 키가 올라갈 일도 없습니다. 음성은 Gemini에 바로 보내 인식과 파싱을 한 번의 호출로 끝냅니다.

| 경로 | 담당 | 내용 |
| --- | --- | --- |
| src/features/input/ | A | 입력 버튼, 녹음, 타임라인, Gemini 파싱 프롬프트·스키마 |
| src/features/mission/ | B | 미션 카탈로그, 판정 함수, 미션 카드, 축하 연출 |
| src/features/reward/ | B | 리워드 달력, 스트릭, 배지 |
| src/shared/ | 멘토 | 계약 타입, 이벤트 버스, 날짜 유틸, 기록 조회, Gemini 호출, 로그인, 목업 데이터 |
| supabase/migrations/, supabase/demo/ | 멘토 | 테이블, 뷰, RLS, 시연 초기화·시드 SQL |
| src/app/ | 멘토 | 오늘·달력·설정(API 키 입력) 화면 조립 |

멘토는 1\~2일차에 시연 문장의 기록 예시를 `src/shared/mocks/`에 넣어 둡니다. B는 A의 입력 기능 없이도 이 목업으로 판정과 연출을 개발합니다.

## 공유 계약

A와 B는 아래 계약만 보고 개발합니다. 이 코드는 멘토가 1\~2일차에 `src/shared/types/contract.ts`로 만들어 두므로, A·B가 직접 짤 필요는 없습니다. AI 도구에는 "contract.ts의 타입을 그대로 import해서 써 줘"라고 요청하면 됩니다.

계약을 바꿔야 하면 '협업 규칙'의 계약 변경 절차를 따릅니다.

### 기록(Record)

A가 만들고 B가 읽는 데이터입니다. 입력 한 번이 기록 여러 개가 될 수 있습니다. 예를 들어 "점심에 싸이버거 먹고 스쿼트 했어"는 식사 기록 1개와 운동 기록 1개가 됩니다.

```ts
export type RecordKind = 'meal' | 'exercise' | 'water';
export type InputSource = 'voice' | 'text' | 'photo' | 'quick' | 'health'; // quick: 빠른 기록 버튼, health: 휴대폰 걸음 수

// 미션 판정에 쓰는 닫힌 목록. 추가·변경은 계약 변경 절차를 따른다.
export type FoodTag =
  | 'fried'             // 튀김
  | 'sugary_drink'      // 가당 음료(콜라, 주스 등)
  | 'zero_sugar_drink'  // 제로 음료
  | 'carbonated'        // 탄산
  | 'alcohol'
  | 'snack';

export type ExerciseCode = 'squat' | 'pushup' | 'walking' | 'running' | 'cycling' | 'other';

export interface FoodItem {
  name: string;       // 화면 표시용, 예: "싸이버거"
  quantity: number;   // 1
  unit: string;       // "개", "공기", "잔"
  kcal: number;
  carb_g: number;
  protein_g: number;
  fat_g: number;
  tags: FoodTag[];
}

export interface ExerciseItem {
  name: string;        // 화면 표시용, 예: "스쿼트"
  code: ExerciseCode;  // 판정은 name이 아니라 code로 한다
  body_parts: string[];
  sets?: number;
  reps?: number;       // 세트당 횟수
  duration_min?: number;
  steps?: number;
  kcal_burned: number;
}

export interface HealthRecord {
  id: string;
  user_id: string;
  day_key: string;      // 'YYYY-MM-DD', Asia/Seoul 기준. DB가 occurred_at으로 자동 계산(앱은 넣지 않음)
  occurred_at: string;  // 먹거나 운동한 시각(ISO). 입력한 시각과 다를 수 있음
  kind: RecordKind;
  source: InputSource;
  raw_text: string | null;     // 음성 인식 결과 또는 입력 문장
  foods: FoodItem[];           // kind = 'meal'
  exercises: ExerciseItem[];   // kind = 'exercise'
  water_ml: number | null;     // kind = 'water'
  confidence: number;          // 0~1, 파싱 확신도
  created_at: string;
}
```

### 기록 변경 이벤트

A는 기록 저장·수정·삭제가 DB에서 성공한 뒤에만 이벤트를 1회 발행합니다. B는 이 이벤트를 받으면 그 날짜의 기록 전체를 다시 읽어 판정합니다. A는 B의 코드를 import하지 않고, B도 A의 코드를 import하지 않습니다.

```ts
export interface RecordsChangedEvent {
  type: 'records:changed';
  day_key: string;
  reason: 'created' | 'updated' | 'deleted';
  record_ids: string[];
}
```

### 미션 결과

```ts
export type MissionSlot = 'diet' | 'life' | 'exercise';
export type MissionStatus = 'in_progress' | 'success' | 'failed';

export interface DailyMission {
  id: string;
  user_id: string;
  day_key: string;
  slot: MissionSlot;
  mission_code: string;            // 카탈로그 코드, 예: 'protein_min'
  params: Record<string, number>;  // 예: { target_g: 40 }
  status: MissionStatus;
  achieved_at: string | null;
}
```

### DB 테이블

| 테이블 | 쓰기 | 읽기 | 용도 |
| --- | --- | --- | --- |
| records | A | A, B | 기록 저장 |
| daily\_missions | B | B | 날짜별 미션 3개와 판정 결과 |
| v\_day\_status (뷰) | 없음 | B | 날짜별 성공 미션 수, 달력·스트릭 계산용 |
| user\_badges | B | B | 배지(P1) |

모든 테이블에 user\_id를 두고 행 수준 보안(RLS)으로 본인 행만 읽고 쓰게 합니다. 테이블·뷰 생성과 변경은 멘토가 마이그레이션으로 관리합니다.

## 모듈 상세 설계

### A: 쉬운 입력 파이프라인

입력 하나는 4단계를 거쳐 기록이 됩니다. AI 호출은 `src/shared/gemini.ts`의 `generateJson`으로만 하고, 키는 설정 화면에서 입력한 값을 씁니다.

1. 입력: 마이크 버튼(녹음), 텍스트 창, 카메라(P1) 중 하나로 받습니다.
2. 인식·파싱: 텍스트, 녹음 파일, 사진을 Gemini에 한 번에 보내 계약의 ParseResult(JSON)로만 답하게 합니다. 태그와 운동 코드는 responseSchema의 enum으로 계약 목록 안에서만 고르게 합니다.
3. 저장: 검증을 통과한 기록을 records 테이블에 저장합니다. confidence가 낮은 항목도 저장하되 타임라인에 '확인 필요' 표시를 붙입니다.
4. 알림: 저장 성공 후 records:changed 이벤트를 1회 발행하고 타임라인을 갱신합니다.

| 구분 | 파싱 함수(A가 src/features/input에 작성) |
| --- | --- |
| 입력 | text, audio(base64), image(P1) 중 하나 + 현재 시각 |
| 출력 | contract의 ParseResult(transcript, records: NewHealthRecord[], warnings) |
| 실패 | 키 없음, 인식 실패, 스키마 불일치 시 records는 빈 배열, warnings에 사유 |

"점심에"처럼 시간 표현이 있으면 현재 시각 기준으로 occurred\_at을 정합니다. 시간 표현이 없으면 입력 시각을 씁니다.

### A: 빠른 기록 버튼과 걸음 수

운동 기록을 쉽게 하는 방법은 운동 기록·헬스 데이터 검토 결과를 따릅니다.

- 빠른 기록 버튼(P0): 최근 운동 칩 3개를 탭하면 AI를 거치지 않고 바로 저장합니다. source는 'quick'입니다.
- iPhone 걸음 수 자동 반영(P1): 앱을 열 때 오늘 0시부터의 걸음 수를 읽어, 하루 기록 1개를 덮어씁니다. source는 'health'입니다.
- 걸음 수는 kind='exercise', code='walking' 항목의 steps에 담습니다. DB가 health 기록을 하루 1개로 제한하므로 upsert로 덮어씁니다.
- 건강 앱(Apple 건강, Health Connect) 연동은 개발 빌드가 필요해 발표 이후로 미룹니다.

### B: 미션 판정

판정은 순수 함수 하나로 만듭니다: `evaluateMissions(missions, records, now)` → 미션별 상태. 이벤트를 받을 때마다 그날 기록 전체로 처음부터 다시 계산합니다. 누적 방식보다 단순하고, 기록을 고치거나 지워도 결과가 틀어지지 않습니다.

미션은 성공을 확정할 수 있는 시점에 따라 세 유형으로 나눕니다. 3주 일정의 P0은 도달형만으로 만듭니다. 도달형은 기준에 닿는 순간 바로 성공이라 가장 단순하고 시연 장면과도 맞습니다.

회피형과 구간형은 P2입니다. 하루 마감은 자정(Asia/Seoul) 또는 사용자가 '오늘 마감'을 누른 시점입니다.

| 유형 | 성공 확정 | 실패 확정 | 화면 표시(마감 전) |
| --- | --- | --- | --- |
| 도달형 | 누적값이 기준에 닿는 즉시 | 마감 시 미도달 | 진행률(예: 32/60g) |
| 회피형 | 마감 시 | 위반 기록이 들어오는 즉시 | 진행 중 |
| 구간형 | 공복 12시간이 지난 시점 | 마감 시 미충족 | 경과 시간 |

| 코드 | 미션 | 슬롯 | 유형 | 판정 규칙 |
| --- | --- | --- | --- | --- |
| protein\_min | 단백질 {target\_g}g 채우기 | 식단 | 도달형 | 오늘 foods의 protein\_g 합 ≥ target\_g |
| no\_fried\_dinner | 저녁 튀김 건너뛰기 | 식단 | 회피형 | 17시 이후 식사에 fried 태그 없음 |
| no\_sugary\_drink | 가당 음료 안 마시기 | 식단 | 회피형 | sugary\_drink 태그 없음(제로 음료는 통과) |
| water\_min | 물 {target\_ml}ml 마시기 | 생활 | 도달형 | water\_ml 합 ≥ target\_ml |
| fast\_12h | 12시간 공복 유지 | 생활 | 구간형 | 전날 마지막 식사부터 오늘 첫 식사(없으면 현재)까지 12시간 이상 |
| squat\_min | 스쿼트 {target}개 하기 | 운동 | 도달형 | code가 squat인 항목의 sets×reps 합 ≥ target |
| steps\_min | {target}보 걷기 | 운동 | 도달형 | 자동 걸음 수와 입력한 걸음 수 합계 중 큰 값 ≥ target |

미션 배정은 P0에서 고정 세트(단백질, 물, 스쿼트)로 시작합니다. (user\_id, day\_key, slot)이 유일하므로 upsert(ignoreDuplicates)로 배정해 이미 있는 행(시연 시드 포함)을 덮어쓰지 않습니다. 시연 장면과 같은 세트라 테스트도 쉽습니다. AI 미션 추천은 P2이며, 하더라도 AI는 카탈로그 코드와 목표값만 고르게 합니다.

### B: 달력과 스트릭

- 날짜 상태는 그날 성공한 미션 수(0\~3)입니다. 3이면 완수 스탬프를 찍습니다.
- 스트릭은 3개를 모두 완수한 날이 끊김 없이 이어진 일수입니다. 오늘이 아직 완수 전이면 어제부터 셉니다. 그래야 낮 동안 스트릭이 0으로 보이지 않습니다.
- 축하 연출은 상태가 in\_progress에서 success로 바뀌는 순간에만 재생합니다. 이미 연출한 미션 id를 기억해 화면 재진입이나 재계산 때 반복되지 않게 합니다.

## 협업 규칙

main에는 멘토만 merge하고, 모든 변경은 PR과 멘토 승인을 거칩니다. 초심자 팀이므로 Git 명령어를 외우기보다 GitHub Desktop이나 Claude Code에게 맡기고, 어려운 일(충돌 해결, 되돌리기)은 멘토가 처리합니다.

### 브랜치와 PR

| 브랜치 | 용도 | 만드는 사람 |
| --- | --- | --- |
| main | 시연 가능한 상태 유지, 직접 push 금지 | 멘토 |
| feat/input-\* | 쉬운 입력 작업 | A |
| feat/mission-*, feat/reward-* | 미션·리워드 작업 | B |
| contract/\* | 공유 계약·DB 변경 | 멘토 |
| fix/\* | 버그 수정 | 누구나 |

- PR 하나에는 체크리스트 항목 1개만 담습니다. AI 도구는 큰 변경을 한 번에 만들기 쉽으니, 화면 하나나 기능 하나 단위로 끊어 달라고 요청합니다.
- 작업을 시작하기 전에 최신 main을 받습니다. GitHub Desktop에서 'Fetch origin' 후 'Pull'을 누르거나, Claude Code에게 "main 최신 내용을 받아 줘"라고 말합니다.
- 충돌(Conflict) 메시지가 나오면 직접 고치지 말고 멘토에게 알립니다.
- merge 조건은 CI(문법 검사, 타입 검사, 테스트) 통과와 멘토 승인 1건이며, 멘토가 squash merge로 합칩니다.
- 리뷰와 merge는 하루 한 번 정한 시간에 몰아서 합니다.
- 저장소에 `.github/CODEOWNERS` 파일을 두고 `* @멘토GitHubID` 한 줄을 넣은 뒤, 브랜치 보호에서 코드 오너 리뷰를 필수로 켭니다(멘토 작업).

### 계약 변경 절차

1. 계약을 바꿔야 할 것 같으면 코드를 고치기 전에 멘토에게 먼저 말합니다.
2. 멘토가 contract/\* 브랜치에서 계약 파일(또는 DB 마이그레이션)만 바꾸는 PR을 올립니다.
3. A와 B가 PR에 확인 댓글을 남기면 멘토가 merge합니다.
4. A와 B는 각자 최신 main을 받아 작업을 이어갑니다. 반영 중 충돌이 나면 멘토가 해결합니다.

기능 PR에는 계약 변경을 섞지 않습니다. 섞이면 리뷰에서 돌려보냅니다.

### AI 코딩 도구 규칙

저장소 루트의 `CLAUDE.md`를 멘토가 관리합니다. 각자의 AI 도구가 이 파일을 읽고 담당 경계를 지키게 하는 것이 목적입니다. 최신 내용은 저장소의 파일이 기준이며, 아래는 요약입니다.

```markdown
# 핏로그 작업 규칙
- 자신의 담당 폴더만 수정한다.
  - A: src/features/input
  - B: src/features/mission, src/features/reward
- src/shared, src/app, supabase 폴더는 수정하지 않는다. 바꿔야 하면 작업을 멈추고 변경안만 제안한다.
- 데이터 타입은 src/shared/types/contract.ts에서 import하고 다시 정의하지 않는다.
- API 키를 코드·.env·커밋에 넣지 않는다. AI 호출은 src/shared/gemini.ts로만 한다.
- 새 패키지를 추가하면 PR 설명에 이유를 적는다.
- 한 번에 화면 하나 또는 기능 하나만 만든다.
- git 충돌이 나면 직접 해결하지 말고 멈춘 뒤 알린다.
- 무엇을 왜 바꿨는지 초심자도 이해할 수 있게 한국어로 설명한다.
- 작업을 마치면 npm run lint, npm run typecheck, npm test를 실행한다.
```

## 멘토 코드 리뷰 체크리스트

멘토는 PR마다 아래 8개 항목을 확인하고, 하나라도 통과하지 못하면 merge하지 않습니다.

| 확인 항목 | 통과 기준 | 이유 |
| --- | --- | --- |
| 담당 경계 | 자기 담당 폴더 밖 변경이 없음 | 동시 작업 중 충돌 방지 |
| 계약 준수 | 타입을 contract.ts에서 import하고, 태그·미션 코드를 임의 문자열로 쓰지 않음 | A·B 사이 데이터 불일치 방지 |
| 비밀 정보 | Gemini 키·service\_role 키가 코드와 커밋에 없음 | 키 유출로 인한 비용·보안 사고 방지 |
| 예외 상태 | 로딩, 실패, 빈 화면 처리가 있음 | 시연 중 멈춘 화면 방지 |
| 테스트 | 판정·스트릭 로직을 바꾸면 테스트도 추가됨 | 순수 함수라 테스트 비용이 가장 낮음 |
| AI 생성 코드 정리 | 쓰지 않는 코드, 남은 목업 데이터, 불필요한 패키지와 로그가 없음 | AI 도구가 자주 남기는 흔적 |
| 데이터 접근 | 앱 코드에서 서비스 키로 RLS를 우회하지 않음 | 다른 사용자 데이터 노출 방지 |
| 시연 회귀 | 시연 시나리오 1회 실행 녹화가 첨부됨 | main의 시연 가능 상태 유지 |

초심자의 PR이므로 리뷰 코멘트는 '무엇을, 왜, 어떻게 바꾸면 되는지'를 구체적으로 남깁니다. 같은 지적이 두 번 나오면 CLAUDE.md 규칙에 추가해, 다음부터는 AI 도구가 알아서 지키게 합니다.

아래 템플릿을 `.github/pull_request_template.md`로 저장하면 PR을 열 때마다 자동으로 채워집니다.

```markdown
## 무엇을, 왜
- 역할표 작업:
- 변경 요약:

## 확인 방법
- [ ] 화면 녹화 또는 스크린샷 첨부
- [ ] npm run lint, typecheck, test 통과
- [ ] 시연 시나리오 1회 실행

## 셀프 체크
- [ ] 담당 폴더 밖 변경 없음
- [ ] 계약 변경 없음(있으면 contract/* PR로 분리)
- [ ] API 키·비밀 정보 없음
- [ ] AI가 만든 코드를 직접 읽고 설명할 수 있음
```

## 통합 검증과 데모 리스크

기획안의 시연 시나리오를 통합 테스트로 그대로 씁니다. 다만 시연 2단계는 지금 설계로는 성립하지 않아 수정이 필요합니다.

### 시연 2단계의 문제와 수정안

- 제로콜라도 탄산음료이므로 '탄산음료 안 마시기'는 규칙상 실패입니다. 미션 이름을 '가당 음료 안 마시기'로 바꾸면 제로콜라가 통과합니다.
- '안 마시기'는 회피형이라 하루가 끝나야 성공이 확정됩니다. 점심 입력 직후 폭죽을 터뜨리려면 도달형 미션이 필요합니다.
- 수정안: `supabase/demo/reset-demo.sql`로 시연 계정을 초기화하고 시드를 넣습니다. 어제까지 10일 연속 완수, 오늘은 물·스쿼트를 미리 달성해 둡니다. 아침 기록도 미리 넣어 두고, 점심 입력으로 '단백질 {N}g 채우기'가 달성되게 합니다. 그러면 3/3 완수로 폭죽과 달력 스탬프가 함께 나옵니다.
- 단백질 목표값 N은 시연 문장을 여러 번 파싱해 본 결과의 최솟값보다 낮게 잡습니다. LLM 추정치가 실행마다 조금씩 다르기 때문입니다.

### 수용 시나리오

1. 시드 데이터가 들어간 시연 계정으로 앱을 엽니다. 오늘 미션 3개 중 2개가 성공, 달력 오늘 칸은 2/3 상태입니다.
2. 마이크 버튼을 누르고 "오늘 점심에 맘스터치 싸이버거 세트 먹고 콜라는 제로로 바꿨어"라고 말합니다.
3. 타임라인에 싸이버거 1개, 감자튀김 1개, 제로콜라 1개가 추가됩니다. 목표는 말을 끝낸 뒤 2초 안팎입니다.
4. 단백질 미션이 성공으로 바뀌며 폭죽이 한 번 재생됩니다.
5. 오늘 칸이 완수 스탬프로 바뀌고 스트릭이 1 늘어납니다.
6. reset-demo.sql을 다시 실행한 뒤 같은 문장을 텍스트로 입력해도 3\~5단계가 똑같이 동작합니다(초기화하지 않으면 단백질 미션이 이미 성공 상태라 폭죽이 나오지 않음).
